## 1. 目标与交付边界

**定位：小型、快速、可靠的 Doris 知识助手。**

- **知识查询：** 回答 Doris 概念、功能、参数、SQL、配置及操作问题；能够按任务组合跨文档或跨章节证据。
- **场景化知识应用：** 用户提供问题描述、日志、SQL、配置文字等；系统提取用户事实，检索 Doris 官方知识，给出有依据的解释、处理建议或必要的澄清。
- **知识事实边界：** Doris 产品事实以已纳入的官方文档为依据；LLM 可以理解、拆解、综合及有条件推理，但不能编造缺失的产品规则或未经验证的集群根因。
- **V1 不做：** 自动连接/操作集群、复杂 Agent 循环、知识图谱、独立 Judge、多模态截图解析、企业账号权限、跨设备协作、自动跨版本知识融合。

## 3. 前端 V1：用户如何使用

**单一对话界面，无需用户先选“知识查询”或“场景分析”模式。**

- **空白新会话首页：** 标题、输入框和三个可点的典型场景引导：①了解功能与用法；②分析报错与日志；③解决配置/功能异常。点击场景**填入可编辑的示例问题，不自动发送**；用户也可直接输入。
- **进入对话后：** 页面展示聊天消息、澄清、答案和可展开的 Doris 文档依据；不把大量检索技术步骤当成用户消息。
- **会话区：** 新建、切换、历史恢复、删除会话；刷新后继续当前会话。单机本地保存即可，不需要账号系统。
- **多行输入：** 可直接粘贴日志、SQL、配置文本；截图、PDF 上传暂不列为必要功能。
- **状态与错误：** 至少区分处理中、需要澄清、完成、证据不足及执行失败；失败时不能把半截答案显示为成功。
- **输入区下方持续提示：** “未指定版本时，默认仅查询当前已收录最新版本（Doris 4.x）；可在提问中指定版本或要求跨版本搜索。” 不强制版本下拉框。

上述页面细节是 V1 推荐落地方式，Codex 不得以旧页面布局取代这套交互要求。

## 4. Session、澄清与版本检索：关键行为契约

### 4.1 Session 和澄清

- 识别本轮是**新问题、补充、纠正、追问、回答澄清**还是切换话题。
- 维护当前有效目标、用户原话支持的事实、待澄清问题、已用证据及尚不确定的推论；**不能把模型推论记作用户事实**。
- 用户补充日志/条件：接续同一问题；用户纠正版本/配置：更新事实，重新审查与该条件相关的证据和结论；切换话题：不继承无关的旧配置或排障假设。
- 只有缺失条件确实阻碍当前检索或正确回答时才追问；能直接回答时不要用固定表单阻挡用户。澄清尽量一次只问最关键事项。
- 本地持久化保存必要消息与结构化状态；不要求复杂诊断状态机或无限历史回放。

### 4.2 版本检索：本日确认，覆盖旧规则

| 用户意图 | 强制检索范围 |
|---|---|
| 未指定版本，当前问题也无有效 Session 版本 | **仅当前已收录最新版本 4.x** |
| 用户明确指定一个版本 | **仅指定版本** |
| 已有同一问题的有效 Session 版本 | 沿用该版本；本轮明确指定的版本优先 |
| “比较 3.x 和 4.x” | **仅 3.x 与 4.x** |
| 明确要求“查所有版本 / 全版本比较” | 才覆盖全部已收录版本 |
| 当前允许的版本范围找不到足够证据 | **不自动扩大范围**；如实说明本次检索范围及证据不足，可建议用户指定其他版本或明确要求跨版本查找 |

- **禁止**因“可能存在版本差异”就自动跨全库搜索、默认追问版本，或把不同版本证据混写。
- 明确的本轮比较请求不必永久改写用户原先的 Session 环境版本；用户明确纠正环境版本则应更新。
- 引文必须标注来源版本；目录版本不自动证明补丁版本适用性。

## 5. 速度与资源约束

- **简单问题走短链路：** 识别明确查询条件 → 在允许版本内检索 → 一次 LLM 生成；无必要时不额外调用 LLM 做拆解。
- **复杂材料才做额外理解：** 长日志、配置组合、多知识子问题需要时才调用理解模型；不设自动多轮检索循环。
- **Session 更新应尽量轻量**，避免每轮重复分析全部聊天历史、全部版本或整个知识库。
- 保留现有索引构建机制；离线 CPU 批量 Embedding 不应作为每次用户提问的处理步骤。
- 记录**首个有效反馈时间、答案完整耗时、LLM 调用次数、检索耗时、P50/P95**；按真实本机结果检查不必要的串行调用。尚未测得基线时不伪造 3 秒/5 秒等硬性 SLA。
- 流式答案可以提升等待感受，但不是 V1 必选项；若采用，不得把未经校验的半截回答当成正式成功。

## 6. 剩余实施工作：建议顺序

| 顺序 | 工作包 | 交付结果 | 依赖/限制 |
|---|---|---|---|
| A | **核实两轮构建真实状态** | 第一轮索引最终检查、第二轮等待验收状态、是否有实际阻断 | 先确认后台任务，禁止重复重建 |
| B | **统一并固化产品交互契约** | 将今天确认的版本规则、Session/澄清、首页引导及性能约束写入新的共同基线；替换冲突的旧规则 | 不开发新的版本知识融合机制 |
| C | **Session 与查询范围接入** | 多会话、恢复、有效事实更新、澄清续接；默认 4.x、指定版本、明确比较才跨版本的检索约束 | 最大限度复用第二轮 RAG 管线；不让 Session 逻辑污染事实证据 |
| D | **正式聊天界面** | 场景引导、可编辑提问、对话历史、澄清、来源查看、错误和等待反馈、输入区版本提示 | 以已定交互为准，不沿用旧页面作默认产品设计 |
| E | **响应优化与全链路验收** | 实际问答、Session 行为、版本范围与延迟数据；必要的阻断问题修复 | 新 768 维索引验收后才能宣称完整 Dense 端到端通过 |
| F | **交付与冻结** | 一键启动/回归说明、修改摘要、真实运行记录、已知限制与遗留项 | 通过约定的最小验收即 V1 收尾，不再新增功能 |

C、D 可在索引构建期间完成不依赖索引的部分；E 的真实全库检索验收必须等 A 完成。执行顺序允许 Codex 在不改变产品契约的前提下按依赖安排。

## 7. V1 最小验收

1. **知识查询：** 简单函数/参数问题可直接回答；跨章节知识能组合，有实际文档引用与版本来源。
2. **场景应用：** 粘贴配置、SQL 或一段日志，能提取用户事实并给出有证据的解释或必要澄清，不编造实际根因。
3. **版本范围：** 未指定仅 4.x；指定单版仅单版；指定两版仅两版；明确全版才全版；查不到也不自动放大。
4. **多轮：** 澄清后回复短句可以接续；补充信息可继续；版本纠正使旧条件失效；新问题不继承不相关事实。
5. **会话与页面：** 新建/切换/恢复/删除有效；首页引导能填入并修改问题；输入下方版本提示明确；答案能查看文档依据及版本。
6. **运行可靠性：** 768 维全量索引通过检查，真实 HTTP/UI/LLM/Dense 链路可运行；失败明确显示，不能用组件测试替代真实回答验收。
7. **速度：** 提供简单和复杂请求的实测耗时及调用次数，排除不必要的重复检索与串行模型调用；不对未测性能作承诺。

## 8. 不重开、不追加的内容

- 不重新选 Embedding/维度（已定 BGE-base-zh-v1.5 / 768）、切片路线、BM25 + Dense + RRF。
- 不重新开发已通过校验的数据处理链，也不因旧实现存在而改变已确认的设计。
- 不做十几个版本的预先语义合并、自动知识演化追踪；不增加“查不到就自动搜所有版本”的回退。
- 不做生产运维 Agent、多模态/权限平台、复杂首页筛选器、独立知识推荐引擎。
- 不盲目再次启动后台索引或等待任务；不把测试 PASS 数量等同于最终实际使用效果。

**交付节奏说明：** 可以以尽快形成可使用的 V1 为目标，但 CPU 索引完成时间、Session 联调和外部 LLM 延迟仍存在不确定性；不能在没有实时进度和联调结果时承诺两天内全部验收。此文件先供方案审阅；确定后再作为 Codex 执行依据。
