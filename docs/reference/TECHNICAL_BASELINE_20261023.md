# DorisRAG V1 技术设计基线

**日期：** 2026-10-23  
**用途：** 独立技术选型与后续代码符合性检查的依据，不是现有代码说明，也不是实施完成证明。  
**当前阶段：** 方案基线形成 → 只读代码差异审查 → 决定复用、修改或替换。

## 1. 研究目的与产品边界

基于 Apache Doris 官方中文知识文档，验证系统如何准确定位和使用特定知识，完成两类任务：

1. **复杂知识查询：** 明确概念、参数、配置和操作问题；重点支持跨文档、跨章节和跨版本的知识定位、组合与引用。
2. **场景化知识应用：** 用户提供异常描述、日志、SQL 或配置文本，模型理解材料、提取事实与约束，检索所需的 Doris 知识，再形成有依据的解释、操作建议或进一步排查步骤。重点关注配置与功能异常、报错排查；性能与资源分析提供文档能支持的解释及排查方向。

**知识来源约束：** Doris 产品事实和规则以本项目纳入的 Doris 官方知识文档为依据。基础模型可以理解语言、提取字段、拆解任务和进行逻辑推理；不能将其参数记忆中的 Doris 事实冒充检索证据。真实运行环境事实来自用户输入，不由文档或模型臆造。文档不足时明确边界。

**本版不承担：** 自动接入或操作 Doris 集群、覆盖所有故障根因、完整运维 Agent、企业权限平台、复杂图谱、独立 LLM Judge、多模态截图解析。此处是 V1 范围，不是否定未来价值。

## 3. 知识处理技术设计

### 3.1 解析和清洗

- 原始文档保持不变，另建可复现的解析产物、检索文本及异常清单；不得静默覆盖原文。
- 识别 front matter 页面标题（大量页面正文没有 H1）、标题层级、段落、列表、代码块、Markdown 表格、少量 HTML 表格、`:::` 提示框及 `<Tabs>/<TabItem>` 范围。
- SQL、Shell、参数名、错误字符串、版本声明和示例结果不得作为展示噪声删除；技术字符串按原样保留。
- `caution/tip` 中的适用条件与其所在规则绑定，Tabs 选项标签与其内部内容绑定，参数表格保留表头及字段对应关系。
- 对源码格式异常采取容错处理并记录原文位置，不以粗糙的行首 ``` 规则吞并后续内容；区分真正的 fenced code、行内三反引号和代码中的 Markdown 样式文本。
- 仅清除确认无知识价值的渲染/导航噪声，不用 LLM 大规模重写技术正文。

### 3.2 切片

**选定方法：** 基于 Markdown/MDX 结构及完整知识单元的切分，配合模型 token 长度控制；不以固定字符长度切片作为主方案。

- 章节为初始边界：短且语义相关的内容可以合并，互不相关的函数或操作不能仅因长度短而拼接。
- 参数说明与默认值/限制条件、SQL 与必要解释/结果、表格表头与数据行尽量构成可理解的证据单元。
- 超长章节进一步按段落、步骤、表格行组、代码逻辑块拆分，关联父章节与原文；遇到单个超长结构，允许多片存储及按需回取原文，不假装一个 Embedding 可以完整编码超过模型上限的内容。
- **Embedding 模型总输入最长 512 tokens（包含标题等附加上下文和特殊 token）**，由所选模型实际 tokenizer 计算，避免隐式截断。初始正文目标约 250–380 tokens 是实施默认值，**并非硬性最小值或经验证的最优参数**；知识单元完整性优先。
- 不要求固定重叠比例；依靠章节/父子位置关联补充上下文。

### 3.3 必要知识元数据

| 字段/逻辑信息 | 作用 |
|---|---|
| 稳定 `doc_id`、`chunk_id` | 去重与原文定位 |
| `title`、`section_path`、`parent_section_id` | 检索上下文与原文回取 |
| `source_path`、原文行号/段落范围 | 回溯证据及引用 |
| `doc_version` | 目录版本 2.1/3.x/4.x |
| `version_note`/适用条件原文 | 文内声明的补丁起止版本、客户端或配置限制 |
| `content_type` | 正文、参数、代码、表格等 |
| `retrieval_text` 与 `source_content` | 索引文字和原始证据分别保留 |

**重要区别：** `doc_version=4.x` 不代表文中每条规则都适用于全部 4.x 补丁。例如 `:::caution` 写有“自 4.1.4 起移除”时，引用时必须保留该限制；无法可靠解析成机器规则时先保存原文并由回答阶段审查，不得凭目录推断补丁精度。

## 4. Embedding 与索引选型

| 决策 | 当前选择 | 依据/约束 |
|---|---|---|
| Embedding | **BAAI/bge-base-zh-v1.5** | 中文技术知识及本机 CPU 条件；用户决定不再专项比较模型 |
| 维度 | **768（原生）** | 与模型匹配，不从文档数推算维度 |
| 最长输入 | **512 tokens** | 模型限制，切片和标题要共用预算 |
| 执行环境 | **本地 CPU** | Ryzen 5 3550H、16 GiB，当前无 PyTorch CUDA |
| 向量匹配 | 小中规模优先精确近邻 | 候选数量为数万级，当前无必须用 ANN 的规模证据 |
| 语义与关键词 | Dense + BM25 | 中文自然语言与精确 SQL/参数/错误码并存 |
| 融合 | RRF | 不直接比较 BM25 和 Dense 的原始量纲 |

具体库名及函数接口不属于产品决策；若以向量内积表示余弦相似度，应保证归一化一致。若改用 768 维新模型，任何旧维度向量必须重新生成，不能直接兼容。

## 5. 检索与查询理解

- **简单知识问答：** 提取明确主题、术语和版本，直接检索；不必强制额外 LLM 拆解。
- **场景问题：** LLM 从用户日志/SQL/配置中提取原始事实、目标、版本、精确技术标识符和缺失条件；必要时形成少量检索子问题。提取的事实与推断必须区分。
- **候选检索：** Dense 检索自然语言语义，BM25 检索普通术语；错误码、参数全名、SQL 函数名等还须保留可用的完整字符串匹配能力，不能默认中文/符号分词器天然做到精确匹配。
- **版本适用：** 指定单一版本则在该版本候选中优先检索；比较多个版本则分版本检索；未注明版本时保留证据版本标识，遇到关键差异应说明条件或询问，不混写版本规则。普通 FAISS Flat 索引不自带元数据过滤，需要检索层提供约束或分组。
- **多证据组合：** 多个知识子问题分别取得候选，RRF 去重融合并按需补充同章节原文。不能默认取全局 Top 1 就足以回答跨文档问题。
- **不预设复杂组件：** 本版不要求 Reranker、知识图谱、递归 Agent 工具循环、独立查询规划服务；没有具体证据前不增加。

## 6. 证据使用与回答

1. 回答时区分 **用户提供的事实**、**文档直接陈述**、**基于多条文档规则的推导**、**目前无法确认的信息**。
2. 每项涉及 Doris 规则/限制/版本的实质结论，能够回溯到适用来源和章节；跨版本结论需分别有版本依据。
3. 可以基于文档事实推导某配置在某条件下的预期行为，但不能把“可能原因”说成已经通过真实集群验证的故障根因。
4. 当知识库不存在必要证据、版本不匹配或证据冲突，说明不足和必要的下一步信息，不调用模型参数记忆补写 Doris 产品事实。
5. 轻量证据引用检查是基础要求；无需第一版单独引入复杂 Judge。

## 7. 三部分的逻辑接口

| 模块 | 输入 | 输出/最小契约 |
|---|---|---|
| **知识处理** | Doris 源文档 | 结构化知识片段、原文与位置、版本及章节元数据、768 维向量和关键词索引 |
| **知识检索** | 原始查询或解析出的子问题、版本/术语约束 | 有标识、版本、来源及原文关联的证据集合；可定位不同检索途径与融合结果 |
| **证据分析回答** | 用户原始材料、提取事实、证据集合 | 答案、引用、适用条件、必要推论或证据缺口 |

此表描述**职责和数据契约，不规定必须拆成三个进程或三个独立服务**。
