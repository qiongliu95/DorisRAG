# DorisRAG V1｜前端交互与 Session 设计基线

状态：V1 设计建议稿（待用户最终确认后作为开发基线）  
依据：已确定的两个产品核心能力（复杂知识查询、场景化知识应用），以及两轮 RAG 后端技术方案。  
原则：交互需求独立于后端实现决定；已有旧页面不构成设计约束。

## 1. 产品交互目标

用户使用**一个对话式入口**，以自然语言提问，也可粘贴 Doris 日志、SQL、配置和报错文字。系统依赖 Doris 知识库提供领域事实，依据用户输入完成解释、知识组合或有条件的排查建议。若缺少关键条件或条件相互冲突，进行必要的澄清；用户可以补充、纠正或继续追问。

V1 不将“检索文档”“场景诊断”拆成两个必须手动选择的模式；系统根据提问自动处理。无强制的版本下拉框、知识主题筛选表单或独立文档选择步骤。用户无需知道知识在哪篇文档。

## 2. 页面结构与基础交互

| 区域 | V1 行为 | 边界 |
|---|---|---|
| 会话列表 | 显示近期会话，支持新建、进入、删除；标题可根据首个有效问题生成并可编辑 | 不建设多用户/团队工作空间 |
| 主对话区 | 按时间展示用户与助手消息、澄清问题、答案；允许继续对话 | 不把技术处理节点大量暴露为聊天消息 |
| 输入区 | 自然语言输入；支持粘贴多行日志、SQL、配置文本 | 截图识别、PDF 上传及自动读取集群不列入 V1 必需能力 |
| 引用查看 | 每条关键 Doris 事实/版本规则显示可展开来源：文档标题、版本、章节、相关原文位置 | 来源文档版本不等于补丁版本适用性已被确认 |
| 系统反馈 | 显示处理中、需要补充、完成、失败；失败有明确原因和可重试入口 | 不把部分输出或处理异常呈现为完整成功 |

答案形式按任务调整：简单问题直接回答；复杂场景在必要时说明用户条件、证据支持的判断、下一步建议与尚未知的条件。不强制每次按固定四段模板展示。

## 3. 澄清机制

- 仅在**关键条件缺失或冲突会明显改变检索范围、答案或操作建议**时进行澄清；不对每次提问先填表。
- 只问当前最关键的一到两个问题。例如“导入失败”可问导入方式与错误信息；“PI() 返回什么”直接回答。
- 若已有足够证据提供部分有用信息，则先给出有依据的部分，再说明还需要什么；不因信息不完美而一律拒答。
- 用户回复“3.1”“是 Stream Load”等短句时，应接续上一轮澄清，不作为新问题。
- 用户问题内版本与明确选择的约束冲突时先确认；未指定版本不默认隐式认定某补丁均适用。
- 澄清内容只针对缺失事实；不能要求用户确认模型推测出的根因。

## 4. Session 管理（不是简单拼接聊天记录）

### 生命周期

- **新建会话**：生成独立 session_id，起始无问题条件；切换会话时状态隔离。
- **持续对话**：同一会话内可提问、补充、追问和纠正；不强制一个会话只能问一件事。
- **话题切换**：出现明显的新问题时，保留聊天历史但不继承旧问题的版本、配置及待验证推论；用户可主动新建会话使两件事彻底分离。
- **刷新恢复**：本地持久保存必要会话记录，刷新页面后可继续当前对话。
- **删除会话**：删除其本地消息及结构化状态；提供明确删除动作，不无提示自动清除。

### 最小会话状态

| 信息 | 处理要求 |
|---|---|
| session_id / 历史消息 | 保持连续会话、恢复与展示 |
| 当前问题概述及目标 | 关联后续“这个参数呢”等追问 |
| 用户明确提供的事实 | 保存版本、错误码、SQL、配置、检查结果等，并能追溯用户原话 |
| 待澄清问题 | 保存正在问什么，以便理解用户下一轮短回答 |
| 有效检索条件与证据引用 | 附带来源版本；条件改变后须重新判断适用性 |
| 可能原因 / 推论及未知项 | 与用户事实分开，不能写回为已证实的运行事实 |

**状态更新规则**：补充则合并；纠正则覆盖相应旧事实并使依赖它的旧检索条件、证据适用判断与推论失效；追问则沿用仍有效的事实；切换话题则隔离前一话题条件。原始聊天消息仍用于展示和追溯。

不要求第一版实现复杂诊断状态机、长期自主规划、多任务并发或对全历史对话的无限重放。

## 5. 前后端接口契约（逻辑层面）

**请求**：`session_id`（新会话时生成）、`user_message`、可选输入文本材料。服务端读取当前有效 Session 状态，对本轮输入判定补充/纠正/追问/新话题，交由既有 RAG 流程处理。

**响应类型**：

- `answer`：本轮有足够依据，返回答案及来源，更新 Session。
- `clarification`：需要补充关键条件，返回具体问题和需要的输入，保存待澄清状态。
- `error` / `incomplete`：服务、证据读取或生成未完成，明确错误，不当作成功答案。

**响应共同信息**：本轮采用的有效问题条件、Doris 证据来源及其版本、必要的未知/条件信息。仅引用来源不等于已证实推论；回答中区分用户事实、文档规则与条件性推导。

上述是接口语义契约，不预设 HTTP 路由、数据库表名或现有代码模块必须如何重构。

## 6. 最小行为验收案例

| 用例 | 期望结果 |
|---|---|
| “PI() 返回什么？” | 直接检索回答，引用 Doris 文档，不强制澄清 |
| “我的 Doris 导入失败了” | 在缺少决定性条件时询问关键问题，而非泛泛堆砌排障知识 |
| 系统追问后用户回答“Stream Load，报 XX” | 接续原问题进行检索和回答，不视为独立新问题 |
| “我刚才说错了，版本是 2.1” | 更新版本，重新核对相关证据，不沿用旧版本判断 |
| “为什么会这样？” | 理解对上一轮结论的追问，继续引用有效来源 |
| 改问无关 SQL 函数 | 不携带此前导入问题的配置及诊断推测 |
| 刷新 / 切换 / 删除会话 | 恢复当前会话、隔离不同会话、删除后无法恢复已删内容 |
| 证据不足、版本冲突、服务失败 | 分别表现为适当澄清/说明未知/错误反馈，不编造确定答案 |

## 7. V1 不纳入

多模态截图识别、企业级账号权限、跨设备同步、自动访问或修改 Doris 集群、多 Agent 自主排障、复杂任务工作台、独立知识主题筛选页面。将来有需求可单独评估，不预留强制实现。

## 8. 与后端基线的关系

**后端技术基线**负责知识处理、索引、检索、证据组织和回答；**本交互基线**负责用户怎样开始/继续问题、澄清时机、Session 状态与页面行为。Session 状态持久化虽影响后端实现，但其行为契约属于本设计，需与 RAG 流程的输入/输出对接。不得以既有旧网页替代交互设计，也不得因旧代码实现而反向更改产品规则。

待用户确认本建议稿后，可作为前端及会话能力的正式实施依据，再针对已有网页做符合性检查与改造。
